# Fork installation and lifecycle changes

This fork keeps all upstream resource kinds, the `zitadel.truvity.io/v1alpha2`
API group and Go module path. Images and charts are published under
`ghcr.io/linasvidziunas`; release tags are explicit, with no automatic tag bot.
CI and release jobs are repository-local. Dependabot replaces the upstream
GitHub App-dependent automation. The source chart versions remain placeholders;
release packaging sets version and appVersion from the tag.

## Zero-click bootstrap for an existing instance

The optional pre-install/pre-upgrade bootstrap Job uses a configuration-defined
Zitadel `SystemAPIUsers` identity to provision a normal machine account, grant
IAM_OWNER, register a machine RSA public key and create the operator credential
Secret. The operator's existing membership verification remains enabled.
This supports an initialized instance; it does not rely on FirstInstance.

### Default: cluster-generated keys

When bootstrap is enabled, it generates two separate 3072-bit RSA keypairs inside
its pod and stores them in a persistent, immutable Secret. It creates the Secret
only if absent and reuses it on retries. No PEM files or key values are required
in Git, Helm values or a local secret workflow.

The system private key signs bootstrap JWTs; its public counterpart is published
as Helm values in a ConfigMap in the Zitadel namespace. The machine private key
authenticates the ordinary operator account after bootstrap. Neither key is
Zitadel's symmetric database-encryption masterkey, a TLS key or a Kubernetes CA key.

Add this reference to the **Zitadel server's Flux HelmRelease**:

```yaml
spec:
  valuesFrom:
    - kind: ConfigMap
      name: zitadel-operator-bootstrap-public
      valuesKey: values.yaml
      optional: true
```

The ConfigMap is generated by bootstrap, not templated into either Helm release.
It carries `reconcile.fluxcd.io/watch: Enabled`, so Flux reloads Zitadel when the
public key appears. Keep the reference optional: Zitadel must start before
bootstrap can add trust. The bootstrap Job retries authentication while the
server rolls out and its IAM projections converge. Do not make the Zitadel
HelmRelease depend on the operator release.

The configuration-defined identity receives `IAM_OWNER` and `ORG_OWNER`.
The bootstrap accesses
the default organization and assigns the operator IAM_OWNER because the full CRD
catalog includes instance-level resources. Use an organization-scoped ordinary
machine credential instead if the deployment should manage only one organization.

Then configure the **operator** chart:

```yaml
config:
  domain: auth.example.com
  binding: iam-owner
credentials:
  secretName: zitadel-operator-credentials
  key: key.json
bootstrap:
  enabled: true
  issuer: https://auth.example.com
  systemUser: gitops-bootstrap
  username: zitadel-operator
  generateKeys: true # default when bootstrap is enabled
  zitadelNamespace: zitadel
  keysSecret: zitadel-operator-bootstrap-keys
  publicConfigMap: zitadel-operator-bootstrap-public
```

Give the operator HelmRelease a timeout longer than `bootstrap.timeoutSeconds`
(default 600), for example `spec.timeout: 15m`, and let it depend on the initially
healthy Zitadel HelmRelease. Install the CRD chart before custom resources.
The keys, output credential and public ConfigMap have no Job/Helm ownerReference;
hook cleanup and chart uninstall do not erase them. The hook's temporary RBAC
allows named Secret reads/Secret creation in the operator namespace and named
ConfigMap reads/updates/ConfigMap creation in the Zitadel namespace. It cannot
read Secrets from the Zitadel namespace.

The generated ConfigMap must not also be managed as a Git manifest. ConfigMaps
or input Secrets belonging to another bootstrap identity are rejected.
On a full rebuild, new keys can authorize the same machine account through
fresh server trust. They are replaceable credentials, not encryption keys needed
to decrypt existing Zitadel data.

Bootstrap reruns verify and reuse the output Secret; they never reset an invalid
credential or rotate it. Existing unrelated output Secrets, human usernames and
insufficient existing IAM memberships cause failure. A failed verification after
creation is retried after Zitadel projections converge. A crash before the output
Secret is persisted may leave an additional registration of the same public key.
The default expiry is `9999-12-31T23:59:59Z` (effectively non-expiring), so no
installation-specific renewal date is required. Set `bootstrap.expires` to an
RFC3339 timestamp if a shorter lifetime is wanted. This does not change the
expiry of an already registered credential.

### Optional: supplied keys

Set `bootstrap.generateKeys: false`, `bootstrap.systemKeySecret` and
`bootstrap.machineKeySecret` to use existing input Secrets instead. Each contains
`key.pem` (PKCS#1 or PKCS#8 RSA private PEM). In this mode configure the system
public key in the server separately under
`zitadel.configmapConfig.SystemAPIUsers.<systemUser>.KeyData` (base64 public PEM),
with `Memberships: [{MemberType: System, Roles: [IAM_OWNER, ORG_OWNER]}]`.
The hook does not create input keys or publish a ConfigMap in supplied-key mode.

## OIDC handoff and grants

`public` and `native` OIDCApp resources now write the generated client ID to their
output Secret, without a client secret. This supports downstream configuration
Jobs such as BookOrbit's application-settings API setup.

```yaml
apiVersion: zitadel.truvity.io/v1alpha2
kind: OIDCApp
metadata:
  name: bookorbit
spec:
  projectRef: {name: books}
  type: native
  authMethod: none
  grantTypes: [authorization_code, refresh_token]
  redirectUris:
    - https://books.example.com/oauth2-callback
    - bookorbit://oauth2-callback
  secretRef: {name: bookorbit-oidc}
  deletionPolicy: Retain
```

Grant types, application type and authentication method are drift-corrected.
Authorization code is required; refresh tokens are opt-in. Type/name conflicts
and lookup errors fail reconciliation rather than creating speculative objects.

Once an application ID is recorded, reconciliation uses that stable ID. Display
name changes update the same application. Moving an existing application to a
different project is rejected; declare a new OIDCApp instead. If the recorded
remote application was deleted, reconciliation reports that error rather than
silently adopting a namesake. Recreate the CR deliberately to provision a replacement.

OIDC output Secrets must be owned by the requesting CR. The controller refuses
an unrelated Secret rather than overwriting it. For an upstream installation,
establish ownership deliberately before upgrading; old Secrets were not stamped
with ownerReferences. Never claim a Secret shared by unrelated applications.
Changing the CR name creates a new Kubernetes identity and does not implicitly
authorize taking another CR's output Secret.

For an adopted confidential client without a stored credential, or an intentional
rotation, set `spec.rotateSecret` to a new nonempty value. Missing credentials no
longer silently trigger rotation. Reusing the same value does not rotate again
after status is saved. A crash after remote rotation but before status persistence
can retry rotation; the output is reconciled before Ready is recorded.

## Retention and deletion

Project and OIDCApp default to `spec.deletionPolicy: Retain`. Use `Delete` to opt
into remote deletion on CR removal. Output Secrets owned by an OIDCApp follow
normal Kubernetes garbage collection; retention refers to the remote identity,
not a backup of confidential credentials.

Other resources using the common lifecycle helpers can opt out of remote cleanup
with `zitadel.truvity.io/deletion-policy: Retain`. Existing singleton policy rules
still apply. Cleanup failures now retain the finalizer and retry instead of
silently dropping it. This intentionally changes formerly best-effort deletion.

For Project inline roles, an omitted/null list leaves roles unmanaged; `roles: []`
is an authoritative empty set and removes all roles. Nonempty lists remain
authoritative. Do not combine this with ProjectRole CRs for the same project.

## Validation

### YAML editor support

`schemas/` contains generated JSON Schemas for all served CRD kinds, plus
`all.json` for mixed-resource files. Associate a schema with your YAML language
server or use a modeline, adjusting the relative path for your manifest:

```yaml
# yaml-language-server: $schema=../schemas/oidcapp-v1alpha2.json
apiVersion: zitadel.truvity.io/v1alpha2
kind: OIDCApp
```

Schemas supply field documentation, completion, enum/type checks and unknown-field
diagnostics. Kubernetes additionally enforces CRD CEL rules at admission.
`just generate` refreshes the CRDs, editor schemas and API reference together.

### Runtime checks

Normal CI builds, vets and runs the Go suite, checks generated schemas and renders
both charts. A separate compatibility job runs Zitadel v4.19.2, PostgreSQL, envtest
(kube-apiserver + etcd) and a Go runner inside disposable containers. It tests
generated-mode public configuration, system-user bootstrap, the default key expiry,
preserved credentials on rerun, native PKCE client handoff,
refresh grants, out-of-band redirect drift, stable-ID rename, explicit confidential
credential recovery, removal of more than 100 roles, retention and opt-in deletion.

Unit tests cover first-time key generation, publication retry, stable trust on
rerun and preservation of foreign/invalid state. The container test uses
pre-seeded disposable keys trusted by its server; it does not simulate a Flux
server rollout.

The runner is `tests/compat/run.sh`; it supports Docker and the Podman-compatible
Docker CLI. It mounts this checkout read-only and copies it inside the container.
Its exit trap removes containers, the temporary key volume and network. Images
remain in the container engine's normal image cache. No Kubernetes binaries,
cluster configuration or test credentials are installed on the host.

The older full integration suite still covers additional resource families using
an explicitly configured test instance; it must not be pointed at production.
